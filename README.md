# 티니핑 도감 (Teenieping Compendium)

브라우저에서 **파일을 직접 열어도** 동작하는 정적 팬 도감 사이트입니다. 별도 빌드/서버가 필요 없습니다.
시즌1~6 및 극장판 **전체 157마리**를 수록합니다.

## 실행
`index.html` 를 브라우저로 열면 됩니다. (더블클릭)

## 페이지
- **`index.html`** — 전체 목록. 검색 + 기수/등급 필터 (상태가 URL 에 남아 뒤로가기해도 유지됨).
  성별은 필터가 아니라 카드의 태그로만 보여 줍니다.
- **`p/<id>.html`** — 개별 티니핑. 대표 이미지·이름·태그(기수·등급·성별·감정)·좋아요·마법·에피소드,
  그리고 1차 관계 목록. ⚠️ 자동 생성 — 빌드 때 내용까지 다 그려 넣는 **정적 페이지**입니다.
- **`quiz.html`** — 이름 맞추기. 난도 3종(🍭 쉬움: 3지선다 / 🍨 보통: 이름 가리기 / 😎 어려움: 실루엣).
  보통·어려움은 3초 카운트다운(비프음) 뒤 정답이 저절로 열리고, 그동안 마이크로 이름을
  말하면 맞혔을 때 O 로 알려 줍니다.
- **`rank.html`** — 인기 차트. 💖 좋아요 · 🔎 조회 순위를 위에서 아래로, 오늘/주간/월간 · 이전·다음 기간 이동.
- **`stats.html`** — 통계. 요약 숫자 + 누적 추이 그래프(최근 7·30·90·360일) + 방문 경로. 꼬리말의 "통계" 로 들어갑니다.
  방문을 세지 않고 공유 버튼·og 태그도 두지 않습니다 — 들여다보는 페이지지 알리는 페이지가 아니라서.
- 상단 바의 **🔮 랜덤핑** — 아무 티니핑이나 무작위로 보여 줍니다.
- 상단 바 오른쪽 끝의 **공유 버튼** — 공유 시트(모바일)를 띄우거나 링크를 복사합니다.

## 데이터 구조 (중요)

`data/teeniepings.js` 는 **자동 생성 파일이라 직접 수정하면 안 됩니다.**
아래 원본들을 고친 뒤 다시 빌드하세요.

```
tools/roster.js      ← 전체 명단 + 등급 (PDF 공식 도감 + 극장판)   [권위 있는 명단]
tools/details.js     ← 특징·관계·영문명 (위키 리서치 상세)
tools/magic.js       ← 마법 설명 (개별 페이지의 '🪄 마법' 칸)
tools/ep-*.json      ← 에피소드 줄거리·회차 (기수별 파일)
tools/gender.json    ← 성별 (나무위키 정보상자에서 수집)
        ↓  node tools/build-data.mjs
data/teeniepings.js
```

### 다시 빌드
```bash
node tools/build-data.mjs     # 데이터
python3 tools/build-og.py     # 미리보기 카드 이미지 (images/og/)
node tools/build-pages.mjs    # 개별 페이지 157개 (p/<id>.html)
```

> 개별 페이지는 **정적 파일이라 빌드해야 반영됩니다.** 이름·마법 설명·관계·이미지를 고쳤다면
> 세 개를 순서대로 돌리세요. `data/teeniepings.js` 만 고치고 빌드를 잊으면
> 목록·퀴즈는 바뀌는데 개별 페이지만 예전 내용으로 남습니다.

`build-pages.mjs` 는 **내용이 바뀐 파일만 다시 씁니다.** 그대로인 파일은 손댄 시각조차
건드리지 않고, 명단에서 빠진 파일(이름이 바뀌어 남은 옛 페이지 등)만 따로 지웁니다.
아무것도 안 고치고 두 번 돌리면 `새로 쓴 것 0개` 가 나옵니다.

> **왜 통째로 지우지 않는가**: 이 저장소가 iCloud Drive 안에 있기 때문입니다.
> 예전에는 `p/` 를 `rmSync` 로 지우고 다시 만들었는데, 그 사이 동기화가 끼면
> 아이클라우드가 지운 파일과 새로 만든 파일을 서로 다른 것으로 보고
> **`고고핑 2.html` 같은 충돌 사본**을 남겼습니다. 지금은 같은 이름에 덮어씁니다.
> (혹시 그런 사본이 남아 있어도 다음 빌드가 "명단에 없는 파일" 로 보고 지웁니다.)

빌드가 하는 일:
- 로스터의 각 이름에 **id 자동 생성**(한글→로마자 변환) — 기존 id/이미지는 `ID_OVERRIDE` 로 고정 유지
- 상세를 `(기수, 이름)` 으로 매칭해 병합 (실패 시 접두어 제거 후 이름 단독 매칭)
- 관계(relations) id 를 최종 id 로 **재매핑**하고, 세트 밖 참조는 제거
- 관계 **양방향 보정** (A→B 가 있으면 B→A 도 추가)
- 마법 설명은 `magic.js` 에서 **이름(nameKo)** 으로 병합 (`magic` 필드)
- 상세가 없는 캐릭터는 마법/에피소드를 비워 두고, 색상은 시즌 색을 변주해 자동 배정
- 이미지 내용의 짧은 해시를 `imgv` 로 기록 → `imageMarkup` 이 `?v=<해시>` 를 붙인다

> **왜 `imgv` 가 필요한가**: GitHub Pages 는 `max-age=600` 으로 응답합니다.
> 목록 페이지는 방문할 때마다 썸네일 157장을 받으므로 브라우저에 전부 캐시됩니다.
> 그림을 고쳐 배포해도 파일 이름이 같으면 캐시된 옛 그림이 계속 보입니다.
> 반면 개별 페이지 이미지는 그 캐릭터를 열어야 받으므로 캐시가 없어 바로 바뀝니다 —
> **같은 배포인데 개별 페이지만 바뀌고 목록은 안 바뀌는 것처럼 보이는 이유**입니다.
> 그림이 바뀌면 해시가 바뀌어 URL 이 달라지므로 즉시 반영되고,
> 그림이 그대로면 해시도 그대로라 캐시가 유지됩니다.

### 상세 정보 추가하기
`tools/details.js` 의 `window.DETAILS` 배열에 추가하면 됩니다. 병합 키는 `nameKo` + `seasonKey`:

```js
{
  id: "kkareuping",          // 리서치용 임시 id (관계 참조에 사용)
  nameKo: "까르핑",
  seasonKey: "jewel",        // emotion | jewel | key | dessert | star | princess
  nameEn: "Tickleping",
  emotion: "짓궂음",
  traits: "특징 설명…",       // 사이트에는 표시되지 않는 리서치 메모
  story: "에피소드 줄거리…",
  relations: [ { id: "joaping", label: "단짝" } ],
  colorHex: "#7CB342"
}
```

### 마법 설명 추가하기
`tools/magic.js` 의 `window.MAGIC` 에 **이름 그대로** 넣으면 됩니다:

```js
window.MAGIC = {
  "까르핑": "마법 깃털 부채로 상대를 간질여 자지러지게 웃긴다. 정작 자신의 약점도 발바닥 간지럼이다.",
};
```

빈 문자열이면 개별 페이지에 "아직 정보가 준비되지 않았어요 🌱" 가 표시됩니다.

> 등급은 `details.js` 가 아니라 **`roster.js` 가 결정**합니다 (royal / legend / villain 배열).
> 등급 종류: **로열 · 레전드 · 일반 · 빌런**

## 이미지

`images/<id>.png` 가 있으면 그 이미지를, 없으면 `colorHex` 기반 **플레이스홀더 SVG** 를 자동 사용합니다.

### 일괄 수집
아래 순서로 실행하면 됩니다. (Node 18+, 외부 패키지 불필요)

```bash
node tools/fetch-images-og.mjs         # 나무위키 대표 이미지(og:image) 수집
python3 tools/balance-size.py --apply  # 배경 여백 정리 + 카드에서 크기가 고르게 보이도록 균형 조정
python3 tools/make-thumbs.py           # 원본 512px 상한 적용 + 썸네일(images/thumb/*.webp) 생성
```

`fetch-images-og.mjs` 는 문서의 `<meta property="og:image">` 를 읽습니다. 나무위키가 지정한
**대표 이미지**라 어떤 그림이 본인 것인지 추측할 필요가 없어 가장 정확합니다.
하츄핑 계열 6종은 문서가 하나로 합쳐져 있어 og:image 만으로는 폼을 구분할 수 없어 `SKIP` 으로 제외합니다.
다만 **구분할 방법은 있습니다.** 하츄핑 문서의 「시즌별 변신 폼」 절에는 폼마다 이미지가 따로 실려 있고
`img` 태그의 `alt` 에 폼 이름이 들어 있습니다 (`하츄핑시즌2-1`, `FLORA-HEARTSPING`, `베리하츄핑`,
`(티니핑5)스타하츄핑`, `프린세스 티니핑 하츄핑`). 이 `alt` 로 매칭하면 6종을 각각 받을 수 있습니다.

배경이 불투명한 이미지(흰 배경 등)는 `tools/cutout.py` 로 오려낸 뒤 위 두 단계를 돌립니다.

> 💡 **더 큰 원본을 찾으려면 문서 이미지를 전부 훑어야 합니다.** og:image 는 200px 안팎으로
> 잘려 있지만, 같은 문서 본문에 500~1000px 원본이 함께 실려 있는 경우가 많습니다.
> 문서의 `i.namu.wiki` 이미지를 모두 받아 **현재 이미지와 48px 축소 비교로 같은 그림인지 확인한 뒤**
> 가장 큰 것을 고르면 됩니다. 이 방법으로 34장을 평균 2.5배 키웠습니다.
>
> ⚠️ 나무위키 HTML 은 **파이썬 `urllib` 으로 받으면 본문이 비어 옵니다.** Node 의 `fetch` 를 쓰세요.

> ⚠️ **og:image 는 정확하지만 가장 크지는 않습니다.** 나무위키 og:image 는 200px 안팎으로
> 잘려 나오는 경우가 많아, 문서 본문에 실린 그림(500px 이상)보다 작을 수 있습니다.
> 일괄 교체할 때는 **기존 이미지보다 큰지 확인하고 덮어써야 합니다.**
> (실제로 이 확인을 빠뜨려 36장이 최대 6배까지 작아진 적이 있습니다.)

### 배경 오려내기 — `tools/cutout.py`
흰 배경 이미지는 모서리에서 flood fill 로 배경을 찾아 투명하게 만듭니다.
이때 **경계를 부드럽게 남기는 것이 중요합니다.** 그냥 알파 0 으로 지우면
알파가 0 아니면 255 인 이분법이 되어, 분홍 카드 배경 위에서 윤곽이 계단처럼 보입니다.
**허용 색차(`TOLERANCE`)를 낮게 잡아야 합니다.** 흰 배경 위의 흰 캐릭터
(고마핑의 흰 모자, 뽀송핑의 양털)는 배경과 색이 거의 같아서, 18~26 으로 두면
flood fill 이 캐릭터 안쪽까지 파고들어 **머리가 뭉텅 지워집니다.** 12 가 적당합니다.

`cutout()` 은 이진 마스크를 1px 침식한 뒤 흐려서 알파 경사를 만듭니다.
침식을 먼저 하는 이유는 경사가 흰 여백이 아니라 캐릭터 안쪽에서 시작하게 해
**흰 테두리(할로)가 남지 않도록** 하기 위해서입니다.

원본 PNG 부터 알파가 이분법인 경우도 있어(나무위키 이미지 일부),
그럴 때는 원본 알파도 함께 다듬습니다.

### 바다 티니핑 배경 — `tools/strip-heart-bg.py`
방울핑·찰랑핑·소라핑만 대표 이미지에 연하늘색 글로우가 깔려 있습니다.
색으로는 구분할 수 없습니다 — 배경 글로우와 머리카락 하이라이트가 둘 다 S≈0, V≈1 입니다.
대신 **경사**로 판단합니다. 글로우는 부드러운 그러데이션이라 이웃과 색차가 거의 없고,
캐릭터 윤곽에서는 색이 확 바뀝니다. 모서리에서 번져 나가되 이웃과의 색차가 3 을 넘으면
멈추게 하면 글로우만 지워집니다.

흰 몸통도 함정입니다. 소라핑은 배와 팔이 거의 흰색이라 '채도가 낮으면 배경' 규칙에
그대로 걸리고, 배 둘레는 부드러운 그림자라 경사 규칙에도 걸리지 않아 **배가 통째로
지워졌습니다.** 가르는 단서는 **색온도**입니다. 배경은 하늘색 글로우가 옅어진 것이라
차갑고(B ≥ R), 몸통 흰색은 분홍이 섞여 따뜻합니다(소라핑 배는 R 이 B 보다 3~19 높습니다).
거의 흰 픽셀은 **차가울 때만** 배경으로 봅니다.

### 이미지 처리 시 주의 — 알파 채널
`canvas.paste(im, pos, im)` 처럼 **RGBA 이미지를 자기 자신을 마스크로** 붙이면
알파가 **제곱**됩니다(200→157, 128→64, 64→16). 파이프라인을 여러 번 돌리면
안티앨리어싱된 윤곽이 계단처럼 깨집니다. 투명 배경에는 마스크 없이 `paste`,
배경색이 있으면 `alpha_composite` 를 씁니다.

예전 방식(참고용으로 남겨 둠):

| 스크립트 | 방식 |
|---|---|
| `fetch-images.mjs` | Fandom 위키에서 문서 대표 이미지를 가져옵니다. 문서 제목이 **정확히 일치할 때만** 채택합니다. |
| `fetch-images-namu.mjs` | 나무위키 문서에는 시즌 전체 티니핑 틀이 실려 있고 `alt` 에 이름이 있습니다. 문서 몇 개로 수십 마리를 한 번에 수집합니다. |
| `fetch-images-namu-unique.mjs` | 마이너 캐릭터는 `alt` 가 `무제63 2024…` 라 이름으로 못 찾습니다. 대신 여러 문서를 모아 이미지 URL 등장 횟수를 세고, **그 문서에만 있는 이미지**(= 본인 프로필)를 고릅니다. |

> **오매칭 방지 원칙**: 세 스크립트 모두 확신이 없으면 채택하지 않습니다.
> 위키 검색은 유사어를 반환하고(`딩동핑` → `빛나핑`), 한 이미지에 두 캐릭터가 함께 담긴 경우도 있어
> **틀린 이미지를 넣느니 플레이스홀더를 두는 쪽**을 택했습니다.

못 받은 캐릭터는 `images/<id>.png` 로 직접 넣으면 자동 반영됩니다.

## 개별 페이지는 왜 정적인가

개별 티니핑 페이지는 빌드 때 내용까지 **다 그려서** `p/<id>.html` 로 저장합니다.
예전에는 `detail.html` 하나가 주소의 `?id=` 를 읽어 JS 로 그렸는데, 두 가지가 문제였습니다.

1. **한 마리를 보려고 157마리를 받았습니다.** `data/teeniepings.js` 는 199KB 인데
   그중 한 마리만 쓰고 버렸습니다. 지금은 페이지 하나가 6KB 남짓으로 자체 완결합니다.
2. **메신저 미리보기가 전부 똑같았습니다.** 카카오톡·슬랙의 크롤러는 자바스크립트를
   실행하지 않습니다. JS 로 그리는 페이지는 크롤러 눈에 빈 껍데기라, 어떤 티니핑을
   공유해도 같은 미리보기가 나왔습니다.

관계 그래프도 빌드 때 SVG 로 미리 그립니다. 157마리 중 118마리는 관계가 아예 없고
나머지도 최대 5개라, 브라우저에서 매번 배치를 계산할 이유가 없었습니다.

목록(`index.html`)과 퀴즈(`quiz.html`)는 그대로 동적입니다. 검색·필터·퀴즈는
전체 데이터가 필요해서 199KB 를 받는 게 맞습니다.

### 메신저 미리보기

```
p/<id>.html          페이지에 og 태그가 박혀 있음
images/og/<id>.jpg   미리보기 카드 1200x630 (목록 카드 모양)
```

> 폴더(`p/<id>/index.html`)가 아니라 파일 하나로 두는 이유: `file://` 로 열었을 때
> 폴더 주소를 누르면 사파리가 브라우저 대신 **파인더를 엽니다.**
> 웹 서버는 폴더 요청에 `index.html` 을 돌려주지만 `file://` 에는 그 규칙이 없습니다.

- 컷아웃 PNG 를 og:image 로 바로 쓰면 투명 배경이 검게 나오는 앱이 있어,
  배경을 깐 JPEG 카드를 `tools/build-og.py` 로 따로 만듭니다.
- `og:image` 는 **절대 주소**여야 합니다. 배포 주소가 바뀌면
  `tools/build-pages.mjs` 와 `tools/build-og.py` 위쪽의 `BASE` 를 고치세요.
- 카카오톡은 미리보기를 오래 캐시합니다. 잘못 올라간 뒤 고쳤다면
  [카카오 캐시 초기화](https://developers.kakao.com/tool/clear/og) 에서 주소를 넣어 지우세요.

### 목록 검색

한 글자면 **이름·감정**만, 두 글자부터는 **마법 설명과 에피소드**까지 뒤집니다.
한 글자에 긴 글까지 넣으면 거의 다 걸립니다 — `핑` 하나로 157마리가 그대로 남아
걸러 주는 것이 없습니다. 두 글자부터는 `눈물`, `타르트` 처럼 이야기 속 낱말로 찾힙니다.

**이름에 걸린 것이 앞에 옵니다.** 긴 글까지 뒤지면 `하츄핑` 하나로 41마리가 나오는데
(남의 줄거리에 그 이름이 나오는 마리까지 딸려 옵니다) 정작 찾던 하츄핑이 뒤로 밀리면
안 됩니다. 뒤에 오는 것들은 버리지 않습니다 — 그 이야기에 나온다는 것 자체가 알 만한
일이라, 이름으로 찾다가 딸려 오는 것이 오히려 재미입니다.

```
"핑"      157마리   이름만 (한 글자)
"하츄핑"    41마리   이름 6 + 남의 이야기에 나오는 35
"타르트"     3마리   이름 0 — 줄거리에서만
```

뒤질 글이 5만 자가 넘으므로(157마리 × 수백 자) 한 번 만든 검색 문자열은 캐시합니다.
글자를 칠 때마다 다시 이어 붙이고 소문자로 바꾸면 그만큼을 매번 훑게 됩니다.

### 말해서 찾기

검색창 오른쪽 끝 마이크 버튼. 브라우저의 음성 인식(Web Speech)으로 **말한 것을 검색창에
넣어 줍니다.** 자판이 아직 서툰 아이가 이름을 말해서 찾을 수 있게 넣었습니다.

- **말하는 도중의 중간 결과도 바로 넣습니다.** 다 말할 때까지 아무 반응이 없으면
  아이는 안 되는 줄 알고 또 누릅니다. 목록도 그때그때 걸러집니다.
- 듣는 동안 버튼이 분홍으로 차오르고 테두리가 번집니다. **다시 누르면 그만 듣습니다.**
- 자판으로 치기 시작하면 듣기를 멈춥니다 — 둘이 같은 칸을 두고 다투지 않게.
- 화면을 떠나면(카드를 눌러 상세로 가기·뒤로 가기) 듣기를 그 자리에서 접습니다.
  `stop()` 은 듣던 것을 마저 풀어 내놓고서야 끝나는데, 그 사이 페이지가 얼어 붙으면
  (bfcache) '듣는 중' 표시를 안은 채 되살아납니다. `abort()` 로 곧바로 끊습니다.
- 인식기가 문장 끝에 붙이는 마침표는 떼어 냅니다. 검색어에는 군더더기입니다.

지우기 버튼은 마이크 **왼쪽**에 둡니다. 마이크는 늘 있고 지우기는 글자를 칠 때만
나타나므로, 늘 있는 쪽을 끝에 붙박아 둬야 누르려던 자리가 어긋나지 않습니다.

> **https 와 마이크 허락**이 필요합니다(GitHub Pages 는 https 입니다).
> 음성 인식이 없는 브라우저(파이어폭스 등)에서는 버튼을 아예 감춥니다 —
> 눌러도 아무 일이 없는 버튼을 남기지 않는다는 점은 읽어 주기 버튼과 같습니다.
#### 들은 말 고치기

티니핑 이름은 사전에 없는 말이라 인식기가 제 나름대로 아는 낱말로 바꿔 놓습니다.
`공쥬핑` → **공주핑**, `하츄핑` → **하추핑**, `까르핑` → **가르핑**.
고치는 규칙은 `js/hear.js` 에 있습니다 — 이름 맞추기의 말해서 맞히기도 같은 규칙으로 견줍니다.

손으로 고른 표를 두지 않습니다. **157마리 전부**를 규칙으로 훑어 "비슷하게 들리는
열쇠"를 만들어 두고, 들은 말의 열쇠가 그중 하나와 같으면 진짜 이름으로 바꿉니다.
새 티니핑이 늘어도 표를 손볼 일이 없습니다.

열쇠는 한글을 자모로 풀어 **귀로 잘 안 갈리는 것끼리 한 자리에 모은 것**입니다.

```
된소리·거센소리를 예사소리로   ㄲㅋ→ㄱ  ㄸㅌ→ㄷ  ㅃㅍ→ㅂ  ㅆ→ㅅ  ㅉㅊ→ㅈ
비슷한 홀소리를 한 자리로      ㅒㅔㅖ→ㅐ  ㅑ→ㅏ  ㅕ→ㅓ  ㅛ→ㅗ  ㅠ→ㅜ
받침은 실제 소리대로 중화      ㅅㅆㅈㅊㅌㅎ→ㄷ  ㅋㄲ→ㄱ  ㅍ→ㅂ …
띄어쓰기는 무시                "공주 핑" 도 같은 열쇠
```

157개 이름이 **156개 열쇠**로 갈립니다. 겹치는 하나(`아야핑` / `아아핑`)는 **아무것도
고르지 않습니다** — 어느 쪽인지 모르는데 하나를 골라 주면 엉뚱한 것을 찾게 됩니다.

말이 끊겼을 때는 이어 줍니다. `하추` 는 `하츄핑` 의 앞머리인데 검색이 글자 그대로
견주는 것이라 그냥 두면 하나도 안 걸립니다. **두 글자 이상이고 앞머리가 걸리는 이름이
딱 하나일 때만** 이어 줍니다 (`프린세스` → `프린세스 하츄핑`, `하` → 그대로).

못 고치면 들은 그대로 둡니다 — `타르트`, `눈물` 처럼 이야기 속 낱말로 찾는 길도
열려 있어야 합니다.

### 목록 상태 유지

목록의 검색·필터는 주소에 담고(`history.replaceState`), 스크롤 위치는 떠날 때 `sessionStorage`
에 남깁니다. 그래서 한 마리를 눌러 들어갔다가 브라우저의 뒤로 가기로 돌아오면 보던 목록이
그대로 남습니다.

> 한때 개별 페이지에 「← 목록으로」 링크가 있어, 목록의 상태를 `?from=` 에 실어 보내 그 링크와
> 관계 목록 링크에 이어 붙였습니다(`js/page.js`). 링크를 없애면서 그 값을 쓸 곳이 없어져 함께
> 걷어냈습니다. 예전 주소에 남은 `from` 은 공유할 때 떼어 냅니다.

## 이름 읽어 주기

이름 옆 동그란 스피커 버튼을 누르면 브라우저 음성 합성이 이름을 읽어 줍니다.
한글을 아직 못 읽는 아이가 혼자 도감을 넘겨 볼 수 있게 넣었습니다.

```
상세 p/<id>.html   제목 옆 · 마법/에피소드 글 끝  (빌드 때 미리 박아 둔다)
퀴즈 quiz.html     쉬움: 선택지 세 개 모두, 처음부터
                   정답이 공개되면 '정답 행' 안에 (아래 참고)
차트 rank.html     순위 이름 옆
목록 index.html    카드 이름 옆 (이름 한 줄 높이에 맞춰 24px 로 줄인다)
```

목록의 카드는 원래 `<a>` 하나였는데, 그러면 이름 옆에 버튼을 둘 수 없어(링크 안의
버튼) 인기 차트의 행처럼 카드를 `<div>` 로 두고 투명한 링크(`.card-hit`)를 위에 겹쳐
깔았습니다.

퀴즈의 **쉬움**은 선택지 세 개에 처음부터 붙입니다. 글을 못 읽는 아이에게는
선택지를 들어 보는 것이 곧 문제를 읽는 것이라, 답을 알려 주는 것이 아닙니다.
**보통·어려움**은 이름 자체가 문제이므로 정답을 공개한 뒤에 만듭니다 —
미리 있으면 눌러서 답을 엿들을 수 있습니다.

### 글 덩어리 읽어 주기

상세 페이지의 **마법 설명**과 **에피소드 줄거리** 끝에도 붙습니다. 이름 버튼과
다른 점이 둘 있습니다.

- **글을 속성에 옮겨 적지 않습니다.** 설명은 수백 자라 `data-speak` 에 그대로
  베끼면 페이지가 그만큼 무거워집니다(157장을 미리 만들어 두므로 더 그렇습니다).
  값 없는 `data-speak` 로 표시만 해 두고, 누를 때 **감싸고 있는 문단의 글**을
  읽습니다. 버튼 안에는 그림(svg)뿐이라 문단 글에 군더더기가 섞이지 않습니다.
- **끝나기를 기다리는 시간이 다릅니다.** `onend` 를 주지 않는 브라우저를 대비한
  보험을 글 길이에 맞춰 잡습니다(`글자 수 × 600ms`, 최소 5초). 이름 한 낱말에
  맞춘 5초를 그대로 쓰면 줄거리를 읽는 도중에 표시가 꺼지고, 그 뒤에 다시 누르면
  멈추는 대신 **겹쳐 읽습니다.** 보험이 먼저 깨어난 경우에도 겹치지 않도록
  누를 때 `speechSynthesis.speaking` 도 함께 봅니다.

설명이 아직 없는 티니핑(`아직 정보가 준비되지 않았어요 🌱`)에는 버튼을 두지 않습니다.

### 눌러서 시작, 다시 눌러서 멈춤

- 읽는 중에 **같은 버튼**을 누르면 멈춥니다.
- 읽는 중에 **다른 버튼**을 누르면 읽던 것을 멈추고 새 이름을 읽습니다.
- **화면이 바뀌면 멈춥니다.** 다른 페이지로 가거나 뒤로 갈 때(`pagehide`, `js/util.js`),
  그리고 한 페이지 안에서 화면이 바뀔 때 — 이름 맞추기의 다음 문제·난도 화면,
  인기 차트의 기간 넘기기, 목록이 다시 그려질 때 — 그 페이지가 `stopSpeaking` 을 부릅니다.

> 크롬은 페이지가 바뀌어도 읽던 소리를 이어 갑니다(합성기가 페이지 밖에서 돕니다).
> 목록에서 이름을 듣다가 그 카드를 누르면 상세 페이지 위에서 목록의 목소리가 마저
> 나오고, 뒤로 가기로 되살아난(bfcache) 페이지는 '읽는 중' 표시를 그대로 안고
> 돌아옵니다. 한 페이지 안에서는 줄이 통째로 바뀌면 읽던 이름의 버튼이 사라져
> 목소리만 남습니다.

지금 읽는 중인 버튼은 **테두리가 번져 나가는 것**으로 표시합니다.
말해서 찾기의 마이크 버튼과 같은 몸짓입니다 — 하는 일은 반대지만
"지금 소리가 오가는 중" 이라는 뜻은 같습니다.

`onend` 를 주지 않는 브라우저가 있어 5초 뒤에 상태를 푸는 보험을 걸어 두는데,
`cancel()` 이 뒤늦게 부르는 `onend` 와 그 보험이 **이미 다음 이름을 읽는 중에
깨어나 남의 상태를 끄지 않도록** `speakSeq` 로 표를 달아 걸러 냅니다.

> `cancel()` 바로 뒤라도 `speak()` 는 미루지 않고 그 자리에서 부릅니다 — 미룰 까닭이
> 없습니다. **iOS 사파리는 첫 발화를 누른 흐름 안에서 해야 그 뒤의 발화를 허용합니다**
> (WebKit 이 iOS 에서만 거는 제한 — 흐름 안에서 한 번 `speak()` 하면 그 페이지에서는
> 풀립니다). 선택지 이어 읽기와 정답 읽기는 첫 발화가 흐름 밖(텀 뒤·3초 뒤)이라, 누른 그
> 순간 소리 없는 발화를 흘려 엔진을 깨워 둡니다(`primeSpeech`). 맥에는 이 제한이 없어
> 맥에서 재 본 것만 믿고 이 깨우기를 뺐다가 아이폰에서 정답 읽기가 조용해졌습니다 —
> 진단 기록에 `speak` 는 있는데 `start` 가 없었습니다.

페이지를 열 때 합성기를 미리 깨우지는 않습니다. 한때 크롬의 첫 `getVoices()` 가 비어 있다고
그때 한 번 불러 두었는데, 맥 사파리는 합성기가 이미 깨어 있는 상태에서 만든 첫 오디오
컨텍스트에 큰 출력 버퍼를 주어 이름 맞추기의 비프가 160ms 늦게 났습니다(아래 "말해서
맞히기"). 크롬은 `lang` 만으로도 맞는 목소리를 고르고, 첫 발화가 목록을 채웁니다.

### 아이콘 — 인라인 SVG

이모지가 아니라 인라인 SVG 스피커입니다. 헤더 공유 버튼과 같은 방식이라
`currentColor` 를 따라가 분홍 테마에 맞고, 기기마다 모양이 달라지지 않습니다.

처음에는 🗣️(말하는 얼굴)을 쓰고 글꼴에 없으면 👄 로 바꿔 그렸는데, 두 가지가 걸렸습니다 —
🗣️ 는 어두운 옆얼굴 실루엣이라 파스텔 카드 위에서 검은 덩어리로 뜨고,
26px 로 줄이면 형태가 뭉개집니다. 대체용 👄 는 톤도 뜻도 어긋났습니다.
SVG 로 바꾸면서 이모지 유무를 캔버스로 확인하던 코드도 함께 없앴습니다.

### 3초 카운트다운 — 보통·어려움

보통·어려움은 정답을 **손으로 열지 않습니다.** 그림이 화면에 나타나면 이름 칸이 3초짜리
막대가 되어 분홍이 왼쪽에서부터 빠져나갑니다. 그동안 마이크가 켜져 있어 아이가 말한
이름이 한가운데 나타나고(아래 "말해서 맞히기"), 다 빠지면 그 자리에 정답 행이 들어옵니다.

> 예전에는 「👆 눌러서 이름 보기」 칸을 눌러야 정답이 나왔습니다. 그러면 그림을 보자마자
> 눌러 맞혀 보는 참 없이 답만 보고 넘어갈 수 있었습니다. 시간을 고정해 두면 문제마다
> 반드시 3초의 **생각하는 참**이 생기고, 그 뒤에는 손을 대지 않아도 답이 옵니다.
> 넘기는 것은 그대로 「다음 티니핑」 버튼입니다(정답을 본 뒤에야 열립니다).

**1초마다 비프음**이 납니다 — 삐·삐·삐, 마지막에 조금 높고 긴 소리와 함께 정답이
열립니다. 막대는 글을 못 읽는 아이에게도 '줄어드는 것'으로 읽히고, 그림을 보느라
막대를 안 보고 있을 때는 소리가 남은 시간을 알려 줍니다.

막대 한가운데에는 남은 초가 **3 → 2 → 1** 로 소리와 같은 박자로 뜨다가, 이름이 들리면
그 자리를 이름에 내줍니다(아래 "말해서 맞히기"). 숫자는 바뀔 때마다 살짝 튑니다
(`count-pop`) — 글자만 바꾸면 애니메이션이 다시 돌지 않아 `js/quiz.js` 가 요소째
갈아 끼웁니다.

```
0초   삐 (880Hz · 110ms)    막대 가득 · 3 (그림이 나타나고 마이크가 정해진 때 — 마이크는 누른 때부터)
1초   삐                    2/3 · 2
2초   삐                    1/3 · 1
3초   띵 (1320Hz · 380ms)   정답 행 · 맞혔으면 O · 이름 읽어 주기 · 도전 한 번 셈
      맞혔으면 띵 대신 딩동 (C6 → E6, 올라가는 장3도)
```

- 소리 파일 없이 **Web Audio 의 발진기**로 냅니다(`js/quiz.js` 의 `beep`). 길이·높이를
  숫자로 다룰 수 있고, 사인파라 귀에 둥급니다. 10ms 만에 켜서 꼬리로 스러지게 하여
  딸깍 소리가 나지 않습니다.
- 막대는 칸 전체입니다(`.countdown-fill`, `transform: scaleX` 애니메이션). 안에 가는
  막대를 따로 넣지 않는 것은 아이 눈에 크게 보이라고. 길이는 `js/quiz.js` 가
  `animation-duration` 으로 넣어 3초라는 숫자를 `COUNTDOWN_MS` 한 곳에만 둡니다.
  칸은 선택지·정답 행과 같은 **흰 알약에 회색 테두리**입니다 — 3초 뒤 정답 행이 들어올 때
  틀은 그대로고 내용만 바뀝니다. 예전의 분홍 점선은 「눌러서 채우는 빈칸」의 표시였는데,
  누르는 칸이 아니게 되면서 뜻을 잃었습니다.
- **그림이 나타난 뒤에 시작합니다**(`whenImageShown`). 웹에서는 원본 PNG 가 내려오는 데
  한 박자가 걸려, 문제가 뜨자마자 돌리면 빈 분홍 칸 위에서 숫자가 먼저 줄어들었습니다 —
  맞혀 볼 그림도 없이 3초가 샙니다. 로컬 파일에서는 그림이 그 자리에서 떠서 눈에 띄지
  않았습니다. 기다리는 동안 막대는 가득 찬 채 서 있고 숫자는 비어 있습니다(`.counting`
  이 붙어야 줄어듭니다). 이미 내려와 있으면(캐시) 곧바로, 못 내려와 플레이스홀더로
  바뀌어도 시작합니다. 기다리는 사이 다음 문제로 가거나 난도 화면으로 나가면 그
  시작은 무효입니다(`countdownSeq`). 첫 문제는 마이크가 정해진 뒤에야 나오고, 문제
  도중에 마이크를 다시 켜는 중이면 그것도 기다립니다(아래 "말해서 맞히기"). 난도를 고른
  직후에는 난도 칸이 맨 위로 올라가는 전환(0.32초)이 끝난 뒤에 시작합니다(`afterTransition`)
  — 칸이 움직이는 사이 막대가 줄고 삐가 나면 쫓기듯 보였습니다. 쉬움은 선택지 읽기가
  0.5초 뒤에 시작해 이미 전환이 끝난 뒤라 따로 기다리지 않습니다.
- 그래서 그림은 **빨리 와야** 합니다. 퀴즈 그림은 `lazy` 가 아니라 곧바로 받고(`eager` ·
  `fetchpriority=high`) — 사파리는 lazy 그림을 스크롤 같은 계기가 있을 때까지 미루기도
  합니다 — 다음 문제의 그림은 지금 문제를 푸는 동안 미리 받아 둡니다(`preloadImage`).
  원본 PNG 는 200KB 를 넘는 것도 있어 폰에서는 몇 초가 걸리기도 하는데, 받아 두면
  캐시에서 바로 뜹니다. 문제 순서는 페이지를 열 때 한 번 섞어 난도를 바꿔도 이어 쓰므로
  첫 문제의 그림도 난도를 고르는 동안 받아 둘 수 있습니다.
- 이름 칸은 이제 **누르는 칸이 아닙니다.** 손 모양도 hover 도 없앴습니다 — 누를 수
  있어 보이는데 눌러도 아무 일이 없으면 아이가 계속 누릅니다.

> **사파리(아이폰)는 사용자가 누른 흐름 안에서 만들거나 `resume()` 한 `AudioContext`
> 만 소리를 냅니다.** 문제는 늘 누른 데서 시작하므로(난도 칸 · 「다음 티니핑」) 그 흐름
> 안에서 `resume()` 으로 깨워 둡니다. 카운트다운은 컨텍스트가 실제로 돌고 **시계가 가는
> 것을 본 뒤에** 시작합니다(`whenAudioReady`) — 허락 창이 뜨는 사이 세워졌다가 깨어나는
> 동안, 또 아이폰이 녹음을 시작하며 오디오 세션을 바꾸느라 상태는 running 인 채 렌더링만
> 1초쯤 멈추는 동안, 그 위에 예약한 첫 비프가 막대보다 늦지 않게. 정작 소리는 그림이
> 나타난 뒤 흐름 밖에서 나는데, 깨어 있는 컨텍스트에서는 그냥 납니다. 비프를 낼 때
> 컨텍스트가 세워져 있으면 그 삐는 건너뛰고 깨우기만 합니다. 소리 없는 조각을 미리
> 재생하는 옛 iOS 용 깨우기는 두지 않습니다 — 맥과 아이폰 모두 `resume()` 만으로 컨텍스트가
> 돌았습니다. 음성 합성기는 다릅니다(위 "읽어 주기" 절의 `primeSpeech`).
> `AudioContext` 가 없는 브라우저나 무음 스위치를 켠 아이폰에서는 소리만 빠지고
> 막대는 그대로 갑니다 — 소리는 막대를 거드는 것이지 대신하는 것이 아닙니다.

> 카운트다운 도중에 난도 칸을 눌러 나가면 그 카운트다운을 **끊습니다.** 두면 숨은
> 화면 뒤에서 3초 뒤에 정답이 열리고 도전 한 번이 세어집니다 — 보지도 않은 문제를
> 푼 것으로 치는 셈입니다(아래 "난도별 도전" 참고).

### 말해서 맞히기 — 보통·어려움

문제 화면에 있는 동안 **마이크가 켜져 있습니다.** 난도 칸을 누른 순간 난도 화면에 머문 채
켜고, 허락이 정해지면 문제 화면으로 넘어가 첫 문제를 내며, 그 뒤로는 문제 사이에도 끄지
않습니다 — iOS 는 인식을 켜고 끌 때마다
알림음을 내는데, 문제마다 켜고 끄니 문제마다 두 번씩 울렸습니다. 아이가 말한 이름이
막대 한가운데에 나타나 남은 초를 세던 숫자를 밀어냅니다 — 말하는 도중의 중간 결과도
바로(말해서 찾기와 같은 까닭). 마이크 표시는 검색창의 마이크와 같은 모양으로 막대
오른쪽 끝 반원의 한가운데에 서고, 듣는 동안 같은 고리가 번집니다.

3초가 되면 **맞혔을 때만** 정답 행의 오른쪽 끝 — 마이크가 있던 자리 — 에 **O** 가
오고, 띵 대신 두 음이 올라가는 **딩동**이 납니다(`chime`). 쉬움에서도 정답 선택지를
고른 순간 같은 딩동이 납니다. 틀렸거나 말이 없으면 아무 표시도 하지 않습니다. 지어낸 이름은 인식기가 자주
어긋나서 맞게 말했는데 X 를 받는 일이 생기고, 말이 없었던 것은 틀린 것이 아닙니다.

- 들린 이름은 **잉크색**입니다(`.heard`). 분홍 막대 위에도, 막대가 빠져나간 흰 바탕 위에도
  읽혀야 하는데 흰색은 바탕에서, 진분홍은 막대 위에서 묻힙니다. 그 자리에 곧 들어올
  정답 이름과 같은 색이라 자리가 이어져 보이기도 합니다.
- 들은 말은 `js/hear.js` 의 `fixHeard` 로 이름으로 고쳐 견줍니다 — 말해서 찾기가 쓰는
  그 규칙입니다(된소리·홀소리 접기, 앞머리·부분열 맞추기). 후보 셋 중 하나라도 정답이면
  맞힌 것이고, 소리 열쇠가 같은 짝(아야핑/아아핑)은 둘 다 정답입니다(`sameName`).
  한 번 맞혔으면 그 뒤에 딴말을 해도 맞힌 것입니다.
- 허락 창이 뜨기 전에 **마이크 안내 팝업**이 먼저 뜹니다(`#micNote`, `<dialog>` 를
  `showModal()` 로). 보통·어려움을 고르면 난도 화면 위에 "마이크를 사용하면 티니핑 이름을
  말해서 맞출 수 있습니다. 마이크를 끄려면 마이크 버튼을 누르거나 페이지를 벗어나면 됩니다"가
  뜨고, 「좋아요」를 누른 그 흐름에서 마이크를 켭니다 — 사파리는 누른 흐름 안에서만 허락을
  묻습니다. 「싫어요」는 마이크를 끈 채로 바로 문제로 가며 허락 창도 뜨지 않습니다. 마이크
  단추는 회색으로 남아, 누르면 그때 켭니다 — 브라우저가 아직 묻지 않았으므로 그때 허락 창이
  뜹니다(브라우저에서 거부했을 때와 다른 점입니다).
  바깥(가림막)을 누르거나 Esc 로 닫으면 아무것도 시작하지 않고 난도 화면에 남고, 다음에
  난도를 고를 때 다시 묻습니다. 둘 중 하나를 고른 뒤에는 이번 방문 동안 다시 묻지 않고,
  브라우저가 이미 허락됐다고 알려 주면(Permissions API) 처음부터 건너뜁니다. 팝업이 열리면
  초점은 단추가 아니라 팝업 자체에 둡니다 — 첫 단추에 두면 사파리가 파란 초점 링을 그려
  「좋아요」가 미리 골라진 것처럼 보였습니다. 키보드로는 Tab 으로 단추에 가고 Esc 로 닫습니다.
- 듣기는 **문제 화면 단위**입니다. 난도 칸을 누른 그 흐름 안에서 `start()` 를 불러야
  사파리가 허락을 묻고 켜 줍니다. 난도 화면으로 나가거나 화면을 떠나면 끄고, 다음 문제로
  갈 때는 끄지 않습니다. 다른 페이지에 다녀와 되살아나면(bfcache, `pageshow`) 다시 켜 봅니다
  — iOS 는 누른 흐름 밖에서 켜는 것을 막을 수 있는데, 그러면 꺼진 채로 두고 다음 문제를
  누를 때나 마이크 단추로 켭니다. 그때의 거부는 '허락 안 함'이 아니므로 접지 않습니다. 저절로 끝나면(긴 침묵·세션 한도·네트워크) 다시 켜되, 곧장
  끝나기를 되풀이하면 세 번까지만입니다. 다시 켤 때는 이미 허락된 뒤라 창은 뜨지 않고
  알림음만 한 번 납니다.
- 결과는 세션 내내 쌓이므로 **문제마다 창을 냅니다.** 문제를 시작할 때 그때까지의 결과
  수를 적어 두고(`hearing.base`) 그 뒤에 온 것만 이번 문제로 봅니다. 3초 판정 뒤에 오는
  것은 다음 문제가 시작될 때까지 버립니다. 정답을 읽어 주는 우리 목소리는 대개 판정 뒤에
  받아 적혀 그대로 버려지고, 「다음 티니핑」을 아주 빨리 눌러 새 문제로 새어 든 것은
  공개한 지 4초 안에 들린 그 이름을 무시하는 것으로 거릅니다(`isEcho`).
- **첫 문제는 마이크가 정해진 뒤에 냅니다** — 실제로 녹음이 시작됐거나(`audiostart`),
  못 켜졌거나(거부·오류·인식 없음). `start` 가 아니라 `audiostart` 를 기다립니다 — iOS 는
  `start` 를 보낸 뒤에 시스템의 음성 인식 허락 창을 한 번 더 띄우고, 녹음은 그 창이 닫힌
  뒤에야 시작합니다. `start` 에서 문제를 냈더니 허락 창 뒤에서 문제가 먼저 떠 있었습니다.
  그때까지는 난도 화면에 머뭅니다 — 허락 창이 문제 위에 뜨면 그 뒤로 문제 모양이 비치고,
  창이 떠 있는 동안 뒤에서 3초가 새면 첫 문제가 마이크 없이 지나가 버립니다. 허락을
  이미 받은 기기에서는 켜지는 데 한 순간이라 차이가 없습니다. 아무 신호도 안 주는
  브라우저가 있을까 봐 30초에는 그냥 냅니다. 문제 도중에 다시 켜는 중이면 2초까지만
  기다립니다. 마이크 표시가 번지는 것도 실제로 켜진 뒤부터입니다.
- 세워진 컨텍스트에 비프를 예약하면 깨어나는 순간 뒤늦게 나므로, 그때는 그 삐를 건너뛰고
  깨우기만 합니다 — 막대와 어긋난 삐보다 없는 삐가 낫습니다. (소리·마이크·읽어 주기의
  흐름을 화면에 적는 진단 모드를 잠깐 두고 맥과 아이폰에서 기록을 받아 아래 지연 보정과
  읽어 주기 깨우기를 찾았고, 다 찾은 뒤 걷어냈습니다.)
- **컨텍스트를 합성기보다 먼저**: 맥 사파리는 음성 합성기가 이미 깨어 있는 상태에서 만든
  첫 오디오 컨텍스트에 큰 출력 버퍼를 줍니다 — 비프가 화면보다 160ms 늦게 났고, 합성기
  전에 만든 컨텍스트는 5ms 였습니다. 마이크·컨텍스트 순서를 바꿔도 그대로였고, 페이지를
  열 때 `getVoices()` 로 합성기를 미리 깨우던 한 줄을 빼자 사라졌습니다(`js/util.js`).
  이제 컨텍스트는 난도 칸을 누르기 시작하는 순간(`pointerdown`)에 만들고, 합성기는 손을
  떼는 클릭에서 무음 발화로 깨웁니다. 먼저 돌고 있는 컨텍스트는 그 뒤에 합성기가 깨어나도
  그대로입니다.
- **출력 지연 보정**: 그래도 장치가 큰 버퍼로 붙으면 소리는 `outputLatency` 만큼 늦게
  스피커에 닿으므로, 그만큼 소리를 먼저 내고 화면은 그 뒤에 바꿉니다. 첫 삐를 먼저 내고
  지연만큼 뒤에 막대와 숫자를 시작하며, 그다음 삐들은 저마다의 눈금보다 지연만큼 앞서 내고,
  정답도 띵이 들리는 때에 엽니다. 40ms 아래는 보정하지 않습니다 — 귀로 못 가르는 차이에
  화면을 늦추면 삐가 숫자보다 앞서 보입니다.
- 인식이 없는 브라우저(파이어폭스 등)나 허락을 받지 못한 기기에서는 마이크 표시를 내지
  않고 카운트다운만 돕니다 — 한 번 거부하면 단추를 눌러도 브라우저가 허락 창을 다시 띄워
  주지 않으므로 남겨 둘 까닭이 없습니다. 마이크는 단추입니다 — 켜고 끄는 것은 대개 문제
  화면이 알아서 하지만, 「싫어요」로 시작했거나 꺼진 채 되살아났을 때 손으로 켜는 길이라
  누르면 끄고 켭니다. 손으로 껐으면(「싫어요」 포함) 다음 문제·다른 난도·뒤로 가기로
  돌아왔을 때도 켜지 않고, 다시 누르면 켭니다.

> 안드로이드 크롬과 iOS 는 인식이 켜지고 꺼질 때 시스템 소리를 냅니다 — 그래서 문제마다가
> 아니라 문제 화면 단위로 켭니다. 마이크 허락 창은 iOS 에서 방문마다 다시 뜰 수 있습니다.
> 소리는 브라우저 제조사의 인식 서버로 갑니다 — 말해서 찾기와 같습니다.

### 정답 행 — 차트 한 줄과 같은 짜임

정답이 공개되면 **그림 · 이름 · 태그칩**을 담은 한 줄이 나옵니다.
태그는 **목록 카드와 같은 셋**(기수 · 등급 · 성별)입니다 — 감정은 넣지 않습니다.
`열쇠 티니핑` 처럼 긴 것이 있어 폰에서 두 줄로 접혔습니다. 인기 차트의
행(`.rank-row`)을 그대로 씁니다 — 같은 것을 두 곳에서 다르게 보여 줄 이유가 없고,
아이는 차트에서 이미 이 모양에 익숙합니다. 순위 숫자와 집계 숫자만 빠집니다.

```
보통·어려움   이름 칸이 이 행으로 바뀐다 — 그림은 뺀다 (큰 그림이 바로 위에 있다)
쉬움          선택지 셋이 저마다 제자리에서 이 행으로 바뀐다
              O/X 는 차트의 집계 숫자가 있던 오른쪽 끝 자리
```

고른 것 하나만이 아니라 **셋 다** 바꿉니다. 나머지 둘도 결국 티니핑이고, 아이는
방금 이름을 들어 본 그 얼굴을 궁금해합니다. 세 줄 모두 그 티니핑 페이지로 가는
바로가기가 됩니다. 고르지 않은 오답에는 표시를 하지 않습니다 —
틀린 것은 내가 고른 하나뿐입니다.

선택지가 이 행으로 **갈아 끼워지므로** 겉모양과 가운데 정렬을 맞췄습니다.
지름은 `--radius-pill`(999px) 하나를 이름 칸·선택지·정답 행이 함께 씁니다.
높이의 절반보다 큰 값을 주면 브라우저가 높이에 맞춰 깎아 주므로, 높이가 서로
달라도 셋 다 캡슐이 됩니다.

> 한때 `33px`(선택지 한 줄 높이 66px 의 절반)을 줬습니다. 선택지는 캡슐이 되지만
> **그보다 높은 정답 행에서는 위아래가 곧은 둥근 네모**가 되어 캡슐이 아니었습니다.
> 같은 *값*이 같은 *모양*을 뜻하지 않습니다.

> `.answer-row` 는 `.rank-row` 와 **붙여** 씁니다(`.rank-row.answer-row`).
> 클래스 하나짜리로 적으면 특정도가 같아, 스타일시트에서 뒤에 오는 `.rank-row` 가
> 이겨서 `border-radius` 와 `margin` 이 조용히 묻힙니다.

O/X 는 글자가 아니라 **같은 틀에 그린 도형(SVG)** 입니다. 글자로 두면 글꼴마다 O 는 둥글고
넓게, X 는 좁게 나와 둘의 폭·높이가 달랐습니다. 획 굵기는 같고, 크기는 **눈에 같아 보이게**
맞춥니다(`MARK_SVG`). 둘을 같은 네모에 꼭 맞추면 모서리까지 뻗는 X 보다 O 가 작아 보여,
O 를 한 치수(바깥 지름 18 → 20, 약 11%) 키웠습니다. 그리고 O 의 바깥 지름을 이름 칸의
마이크 단추(`--mic-size`, 30px)와 같게 그립니다 — 둘이 같은 점에 서므로 3초에 마이크가 같은
크기의 O 로 바뀐 듯 보입니다. X 는 같은 틀이라 함께 커집니다.

O/X 는 오른쪽 끝에 **겹쳐 그립니다**(`position: absolute`). 자리는 마이크가 서 있던
그 점 — 알약 오른쪽 끝 반원의 한가운데 — 입니다. 행 높이만 한 정사각형을 오른쪽 끝에
붙이고 그 안에 가운데 놓으면 행 높이가 얼마든 정사각형의 중심이 곧 반원의 중심이라,
3초에 마이크가 O 로 바뀐 듯 보입니다. 자리를 차지하지 않으므로
그림·이름·태그가 행의 폭을 다 씁니다.

> 예전에는 좌우에 26px 씩 비워 두었습니다(가운데 정렬을 맞추려고 왼쪽에도 같은 폭의
> 빈 칸을 두는 방식). 그 52px 때문에 태그가 들어갈 폭이 줄어 **폰에서 157마리 중
> 71마리가 두 줄로 접혔습니다.** 겹쳐 그리기 + 감정 태그 빼기로 **320px 폰까지
> 157마리 모두 한 줄**입니다. 그래도 글이 O/X 자리까지 닿으면 그 위에 겹쳐 그려지는데,
> 접히는 것보다 낫습니다.

**이름의 가로 자리**는 선택지와 같습니다. 그림이 이름 왼쪽에 붙으므로 그대로 두면
이름이 그 폭만큼 오른쪽으로 밀립니다. 그림과 글 묶음을 그 절반
(`--thumb-lead` / 2, 그림 54 + 간격 8 의 절반)만큼 **`transform` 으로** 왼쪽에
옮겨 맞췄습니다. 이름의 크기(22px)와 읽어 주기 버튼과의 간격(9px)도 선택지와
같게 두었습니다 — 자리만 맞고 크기가 다르면 여전히 튑니다.

> **왜 `transform` 인가**: 처음에는 오른쪽 끝 칸의 기준폭을 그만큼 늘려 가운데를
> 옮겼습니다. 그런데 비워 둔 폭만큼 글이 들어갈 자리가 줄어, **오른쪽에 여백이
> 남는데도 태그가 두 줄로 접혔습니다.** `transform` 은 자리 계산에 끼지 않으므로
> 글은 폭을 그대로 다 쓰고 보이는 자리만 옮겨집니다.

> `transform` 을 준 요소는 겹쳐 깐 링크(`.rank-hit`)보다 **아래**에 그려져, 그 안의
> 읽어 주기 버튼이 링크에 덮여 눌리지 않게 됩니다. 글 묶음을 링크 위로 올리되
> (`z-index: 2`) 클릭은 통과시키고(`pointer-events: none`), 버튼만 클릭을 받게
> 되돌려 놓았습니다.

**행 전체가 개별 페이지로 가는 바로가기입니다.** 예전에는 이름 옆 화살표(`→`)가
그 표시였는데, 바로 아래 「다음 티니핑 →」 버튼과 **같은 글자라 뜻이 갈리지 않았습니다**
— 하나는 "이 티니핑 보러 가기", 하나는 "다음 문제". 화살표를 없애고 누를 수 있는 면을
행 전체로 넓혔습니다. 작은 손에게는 면적이 곧 쓰기 쉬움입니다.

> 정답을 공개한 **그 손가락**이 곧바로 개별 페이지로 이어지면 안 됩니다.
> 링크를 350ms 동안 꺼 두었다가(`.answer-row .rank-hit { pointer-events: none }`)
> `js/quiz.js` 가 `armed` 를 달아 살립니다.

### 버튼 안의 버튼

읽어 주기 버튼은 `<button>` **안에** 넣을 수 없습니다. 파서가 안쪽 버튼을
바깥으로 밀어내 마크업이 깨집니다. 놓이는 자리마다 다르게 풀었습니다.

- **퀴즈 선택지** — 이름 바로 옆, 칸 안에 둡니다. 선택지(`.choice-btn`)는 원래
  `<button>` 이었는데 `role="button"` 인 `<div>` 로 바꿨습니다(눌러서 정답을 열던 때의
  이름 칸이 쓰던 방식).
  `<div>` 안에는 `<button>` 이 들어갑니다. 대신 Enter·Space 처리를 직접 답니다.
- **정답 행** — 인기 차트와 같은 방식(아래).
- **인기 차트** — 행 전체가 `<a>` 였는데, 행을 `<div>` 로 바꾸고 투명한 링크
  (`.rank-hit`)를 위에 겹쳐 깔았습니다. 버튼만 한 겹 더 위로 올려 클릭을 가져갑니다.
- **상세** — `<h1>` 안이라 원래 문제가 없습니다.

> 안쪽 버튼을 눌렀을 때 바깥(선택지)이 함께 반응하지 않아야 합니다.
> `js/util.js` 의 클릭 처리기는 `document` 에 달려 있어 그때는 이미 늦으므로,
> **감싼 쪽**이 `e.target.closest("[data-speak]")` 로 걸러 냅니다.

음성 합성이 없는 브라우저에서는 `<html>` 에 `no-tts` 가 붙어 버튼이 아예 보이지 않습니다.
눌러도 아무 일이 없는 버튼을 남기지 않는다는 점은 좋아요 버튼과 같은 판단입니다.

## 방문·좋아요 통계

GitHub Pages 는 정적 호스팅이라 **서버가 방문을 셀 수 없습니다.**
그래서 세는 일만 Cloudflare Worker 에 맡기고, 사이트는 그 Worker 를 불러 숫자를 받아 옵니다.

```
worker/counter.js     세는 쪽 (Cloudflare Worker + Durable Object)
js/stats.js           받아서 꼬리말에 그리는 쪽
```

저장에 **Durable Object** 를 씁니다. Workers KV 는 무료 한도가 하루 쓰기 1,000 회뿐이고
전역 반영에 최대 1분이 걸려 실시간 표시에 맞지 않습니다. Durable Object 는 무료 플랜에서도
하루 10만 행을 쓸 수 있고, 한 객체 안에서 요청이 차례로 처리되어 센 값이 곧바로 정확히 읽힙니다.

### 영역별로 따로 센다

목록 · 이름 맞추기 · 개별 티니핑을 **서로 독립적으로** 셉니다.
목록의 방문 수는 목록에 들어온 횟수이지 사이트 전체 합계가 아닙니다.

| 페이지 | 꼬리말에 보이는 숫자 |
|---|---|
| 목록 | 오늘/누적 방문 |
| 이름 맞추기 | 오늘/누적 방문 (난도별 도전수는 난도 선택 카드에) |
| 인기 차트 | 오늘/누적 방문 |
| 개별 티니핑 | 누적 조회 (좋아요는 꼬리말이 아니라 이름 아래 버튼에) |

**공유는 세지 않습니다.** 공유 버튼은 그대로 있지만 숫자로 쌓지 않습니다 —
까닭은 아래 [공유를 아예 빼기까지](#공유를-아예-빼기까지).

통계 페이지(`stats.html`)는 **세지 않습니다** — 통계를 보는 행위까지 통계에 섞이지 않도록.
그래서 그 페이지 꼬리말에는 숫자가 나오지 않습니다.

### 방문은 세션(탭) 단위

`sessionStorage` 에 표시를 남겨 **한 세션에 한 번만** 셉니다. 서버 세션도 쿠키도 IP 도 쓰지 않고,
남기는 값은 `"1"` 하나뿐이라 개인을 식별할 수 있는 정보가 없습니다.

```
ping-visited-list / -quiz / -rank      영역마다 하나
ping-visited-page-<id>                 티니핑마다 하나
```

세는 방식은 같지만 부르는 이름은 다릅니다 — 페이지 단위는 **방문**, 티니핑 단위는 **조회** 입니다.
저장 열쇠는 양쪽 모두 `visit` 입니다.

영역과 티니핑이 각각 따로라, 한 세션에서 목록을 보고 몰래핑·라라핑을 열면
목록 1 · 몰래핑 1 · 라라핑 1 이 오릅니다. 같은 티니핑을 두 번 열거나 새로고침하면 오르지 않습니다.

여기서 말하는 세션은 사람이 아니라 **탭**입니다. 같은 사이트를 새 탭으로 열면 새 세션이고,
탭을 닫으면 `sessionStorage` 가 비워져 다음에 오면 다시 셉니다.
저장소가 막히는 환경(사파리 비공개 모드 등)에서는 걸러 내지 못하고 매번 셉니다 —
통계가 조금 부풀더라도 페이지가 깨지지 않는 쪽을 택했습니다.

### 통계 그래프 (stats.html)

`/series?days=30` 으로 날짜별 값을 받아 선 그래프를 그립니다 (`js/chart.js`, 외부 라이브러리 없이 SVG).

**영역마다 색 하나씩, 세 줄입니다.** 색은 dataviz 팔레트의 1~3 슬롯(파랑·주황·청록)이고,
밝은/어두운 모드 각각 검사기를 돌려 **모든 짝에서** 통과를 확인했습니다
(전체-짝 상한이 3색이라 넷째 색을 넣으면 통과하지 못합니다).
색에만 기대지 않도록 **선 끝에 영역 이름을 직접** 붙이고, 범례와 십자선 툴팁을 함께 뒀습니다.

> 공유를 함께 그리던 때는 줄이 여섯이라 **영역 3색 × 선 모양 2종**(방문=실선, 공유=점선)으로
> 묶고, 범례도 그 두 벌로 적었습니다. 공유가 빠져 줄이 셋이 되면서 모양을 나눌 일도,
> 범례를 두 벌로 둘 일도 없어졌습니다.

범례는 **영역 이름 세 칸**이고, 표식 없이 이름을 그 선의 색으로 적습니다. 그래프에서
선 끝에 붙는 영역 이름도 같은 색 글자라 둘이 곧바로 이어집니다. 누르면 그 영역의 선이
켜지고 꺼지며, **마지막 하나는 끌 수 없습니다** — 다 끄면 그릴 것이 없어지기 때문입니다.
밝은 모드에서 청록이 배경 대비 3:1 에 못 미쳐 뜨는 경고도 이 직접 라벨로 해소됩니다.

숫자를 그대로 가져가고 싶으면 **CSV 내려받기**를 쓰면 됩니다.
지금 보고 있는 구간을 그대로 내보내고, 엑셀이 한글을 깨뜨리지 않도록 BOM 을 붙입니다.

**누적선은 화면에서 역산합니다.** Worker 는 날짜별 값과 전체 누적만 주고,
전체 누적에서 구간 안의 합을 빼면 구간 시작 직전까지의 값이 나옵니다.
그래서 구간 밖의 과거 기록까지 반영된 진짜 누적선이 됩니다.
그래프는 누적선만 그립니다 — 날짜별 값은 CSV 로 받을 수 있습니다.

날짜별 열쇠는 목록·퀴즈·순위에만 있습니다(하루 3 개 — 영역마다 방문 하나씩).
티니핑별은 주·월만 쌓으므로 이 그래프에는 나오지 않습니다.

#### 공유를 아예 빼기까지

**공유는 이제 어디서도 세지 않습니다.** 통계 페이지의 요약 숫자·그래프·CSV, 개별 페이지
꼬리말의 "누적 공유", 인기 차트의 📤 공유 순위, 순위 동점을 가르던 종합 점수의 공유
가중치까지 차례로 뺐습니다.

셀 수 있는 것이 우리 공유 버튼을 거친 것뿐이라, 숫자가 실제 공유의 **하한값**인데
얼마나 모자란지도 알 수 없었습니다.

| 어떻게 공유했나 | 셌나 |
|---|---|
| 사이트의 공유 버튼 → 공유 시트 · 링크 복사 | 셈 |
| 브라우저 자체 공유 (사파리 하단 아이콘, 크롬 ⋮ → 공유) | 못 셈 — 우리 js 를 거치지 않음 |
| 주소창에서 복사해 붙여넣기 | 못 셈 |

**세기는 멈추되 쌓아 둔 것은 지우지 않습니다.** Worker 는 이제 공유를 어디서도 세지
않습니다. 다만 저장소에 남아 있는 `:share` 열쇠(`<영역>:share` · `day:<날짜>:<영역>:share` ·
`page:<id>:share` · `d:`/`w:`/`m:` 의 기간별 열쇠)는 그대로 둡니다 —
읽는 곳이 없으니 없는 것과 같고, 지우는 코드를 두면 배포하는 순간 되돌릴 수 없이
사라집니다. 화면에 안 나오는 것과 데이터를 없애는 것은 다른 일입니다.
`series`/`collect` 는 아는 열쇠만 담으므로 남은 공유 열쇠가 응답에 섞이지 않습니다.

**방문 경로는 그대로입니다.** 공유 버튼이 붙이는 `?s=1` 표식도 그대로라, 리퍼러 없는
공유 유입은 계속 `_share` 로 잡힙니다 (아래 [방문 경로](#방문-경로)).

### 방문 경로

통계 페이지 아래에 **어느 주소를 거쳐 들어왔는지** 많은 순으로 보여 줍니다.
기간은 **달력이 아니라 최근 N일** 입니다 (7일 · 30일 · 90일 · 360일).
한 세션에 한 번만 셉니다.

```
ref:d:<날짜>:<주소>       날짜별로만 쌓고, 조회할 때 구간을 합친다
```

달력 주·달로 쌓으면 "최근 7일" 같은 구간을 만들 수 없어 날짜별 한 벌만 둡니다.
열쇠가 날짜순이라 `start`/`end` 로 구간만 훑습니다.

**리퍼러가 있으면 그 주소를 씁니다.** 공유 버튼이 붙인 `?s=1` 표식이 함께 있어도
주소 쪽을 택합니다 — "공유로 들어왔다" 보다 **"어디에 올린 링크였나"** 가 더 알 만하고,
공유였다는 것은 표식 없이도 그 주소를 보면 대개 짐작이 됩니다.

| 무엇 | 열쇠 | 언제 |
|---|---|---|
| 주소 | `t.co`, `google.com` … | 리퍼러가 있음 (`?s=1` 이 함께 와도 이쪽) |
| 공유 링크 | `_share` | 공유 버튼을 거쳤는데 **리퍼러가 없음** — 메신저 유입이 여기 모임 |
| 사이트 안에서 이동 | — (세지 않음) | **표식이 붙어 있어도** 세지 않음 |
| 그 밖 | — (세지 않음) | 리퍼러도 표식도 없음 (앱·북마크·주소 입력) |

그래서 `_share` 는 **공유 유입의 전부가 아니라 "어디서 왔는지 알 길이 없는 공유"** 입니다.
트위터에 올린 공유 링크로 들어오면 `_share` 가 아니라 `t.co` 로 잡힙니다.

**밖에서 들어온 것만 셉니다.** 공유 링크를 우리 페이지 안에서 눌러 봐야 새 방문자가
온 것이 아니므로, 리퍼러가 우리 사이트면 표식이 붙어 있어도 세지 않습니다.

**리퍼러도 표식도 없으면 아예 세지 않습니다.** 어디서 왔는지 알려 주는 것이 없어 목록에
쓸 데가 없는데, 카카오톡 같은 인앱 브라우저가 리퍼러를 보내지 않아 **수만 가장 크게**
쌓였습니다. 그러면 막대 길이의 기준(max)을 그것이 가져가 나머지 주소가 전부
납작해집니다. `js/stats.js` 의 `referralHost()` 가 `null` 을 돌려주고, 그러면
요청 자체를 보내지 않습니다.

> Worker 쪽도 `_direct` 를 받지 않습니다 — 옛 js 가 캐시에 남은 브라우저가
> 보내더라도 조용히 흘려보냅니다 (세지 않을 뿐 오류는 아닙니다).
> 세기 전에 쌓여 있던 기록(2일치 12건)은 한 번 지웠습니다.

메신저 유입은 주소로 알 수 없어 `_share` 에 모입니다. 주소창에서 복사해 보낸 링크는
표식도 없고 리퍼러도 없어 아예 잡히지 않습니다.

표식은 세고 난 뒤 `history.replaceState` 로 주소에서 지웁니다 — 남겨 두면 받은 사람이
그 주소를 다시 공유하거나 북마크할 때 계속 공유 유입으로 잡힙니다.

주소는 점으로 나뉜 마디가 둘 이상이고 각 마디가 영숫자로 시작·끝나야 열쇠에 들어갑니다.
그러지 않으면 아무 문자열이나 저장소에 쌓입니다.

### 좋아요

개별 티니핑 페이지의 이름 아래 버튼입니다. 방문과 달리 **사람이 스스로 누르는 값**이라
세는 방식이 다릅니다.

```
POST /hit?type=like&scope=page&page=<id>
```

- **기기 단위로 한 번.** `sessionStorage` 가 아니라 `localStorage` 에 `ping-liked-<id>` 를
  남깁니다 — 탭을 새로 열 때마다 또 눌릴 수 있으면 숫자가 의미를 잃습니다.
- **되돌리는 길은 두지 않았습니다.** 빼는 요청을 받으면 남의 숫자를 깎는 데 쓰일 수 있습니다.
  대신 잘못 눌러도 잃는 것이 없도록 좋아요는 어디서도 부정적으로 쓰이지 않습니다.
- **개별 티니핑에만 있습니다.** 목록·퀴즈·순위에는 누를 대상이 없어 `scope` 가 `page` 가 아니면
  Worker 가 조용히 무시합니다.
- 버튼은 **숫자를 받아 온 뒤에야 나타납니다**(`js/page.js`). Worker 가 꺼져 있으면 눌러도
  아무 일이 없는 버튼이 남는 편보다 아예 안 보이는 편이 낫습니다.
- 숫자는 `js/stats.js` 가 이미 받아 온 `/stats?page=<id>` 응답을 `onStats(fn)` 으로
  넘겨받아 씁니다 — 같은 것을 두 번 물어보지 않도록. 이벤트를 곧장 듣지 않고 이 함수를
  거치는 까닭은 아래 "이름 맞추기" 절에 적었습니다(신호가 먼저 지나갈 수 있습니다).

자유 서술 피드백은 두지 않았습니다. 익명 텍스트를 받으면 스팸·욕설을 거르는 일이 따라오는데,
아이가 보는 페이지에서 그 위험을 감수할 이유가 없습니다.

### 순위 (rank.html)

티니핑별 조회·좋아요는 **누적 · 오늘 · 주간 · 월간** 네 벌로 쌓습니다.

```
page:<id>:<kind>            누적
d:<YYYY-MM-DD>:<id>:<kind>   오늘 (한국 시각)
w:<그 주 월요일>:<id>:<kind>   주간 (월요일 시작)
m:<YYYY-MM>:<id>:<kind>      월간
```

**열쇠는 실제로 본 티니핑에만 생깁니다.** 157 마리를 매일 다 본다면 하루 314 개가
늘겠지만, 실제로는 그날 본 만큼만 늘어납니다. 순위를 뽑을 때도 해당 기간 접두어만
훑으므로 최대 314 개만 읽습니다.

```
https://<worker 주소>/rank?period=day|week|month[&at=<기간>][&limit=10]
```

**조회·좋아요 순위를 한 번에** 돌려줍니다(`visit`, `like`). 저장소는 한 번만 훑고
두 벌로 줄 세우므로 요청도 한 번이면 됩니다.

- `at` — 볼 기간. 오늘은 `2026-08-21`, 주는 그 주 **월요일**(`2026-08-17`), 월은 `2026-08`.
  없으면 이번 기간.
  형식이 맞지 않으면 무시하고 이번 기간을 봅니다 (열쇠에 아무 문자열이나 들어가지 않도록).
- 순위는 각각 그 수치의 내림차순입니다. **그 수치와 종합 점수가 둘 다 같아야 같은 순위**입니다 —
  공동 1위가 둘이면 그다음은 2위가 아니라 3위입니다.
  차례도 순위도 수치가 같을 때는 **종합 점수**가 가릅니다.

  ```
  종합 점수 = 좋아요 × 10 + 조회 × 1
  ```

  들인 수고만큼 점수를 줍니다 — 조회는 페이지를 열기만 해도 오르고, 좋아요는 기기당
  한 번뿐이라 더 진심에 가깝습니다.
  종합 점수까지 같으면 id 순입니다(`collect` 가 열쇠 순서로 돌려주고 `Array.sort` 가
  안정 정렬이라 그대로 남습니다).

  **좋아요가 나란히 5여도 조회수가 다르면 순위를 가릅니다.** 기준이 같을 때 점수를
  가르는 것은 다른 쪽 수치뿐이라, 조회 순위도 같은 이치로 조회가 같고 좋아요가 다르면
  갈립니다. 줄은 이미 그 차례로 서 있는데 순위 숫자만 같으면 왜 위아래가 갈렸는지
  알 길이 없습니다. 인기 차트의 행에는 두 값이 다 나오므로 — 그 목록이 줄 세우는 값이
  위에 굵게, 다른 값이 그 아래에 — 갈린 까닭이 그 자리에서 보입니다.
  순위는 상위 N 개를 자르기 **전에** 전체에서 매깁니다 (자르고 매기면 공동 순위가 어긋납니다).
  해당 수치가 0 인 티니핑은 그 순위에 넣지 않습니다 (좋아요 0 인 티니핑이 좋아요 순위에 오르지 않도록).
- **직전 기간과 비교한 오르내림**(`delta`)을 각 줄에 붙입니다. 화면에는 ▲2 · ▼1 · – · 신규 로 나옵니다.
  순위는 그 기간 전체에서 매기지만, **견주는 것은 차트 안(상위 `limit`)까지**입니다 — 10 위 밖에
  있었으면 "신규" 입니다. 차트가 보여 주는 것은 열 자리뿐이고 오르내림도 그 안의 이야기라서,
  지난 기간 40 위였다가 3 위가 된 줄의 ▲37 은 읽히지 않는 데다 밖에서 뒤척인 차이까지 숫자에
  섞입니다. 자르는 자리는 이번 기간과 같은 `limit` 입니다.
  직전 기간에 기록이 아예 없으면 비교할 것이 없으므로 표시하지 않습니다.
- 응답의 `now` 로 지금이 어느 기간인지 알려 주므로, 페이지는 **다음 기간 단추를
  이번 기간에서 잠급니다.** 이전 기간은 제한 없이 거슬러 갈 수 있고 기록이 없으면 빈 목록입니다.

기간은 달력 기준입니다 — 주는 **월요일 시작**, 월은 1일 시작(모두 한국 시각).
최근 7일이 아니라 달력 주이므로 월요일이 되면 자동으로 새 기간이 시작됩니다.

주간·월간은 이 기능을 넣은 시점부터 쌓입니다. 그전 기록은 개별 페이지의 누적 숫자에만 있습니다.

**난도별 도전** 은 **정답을 본 순간** 한 번으로 셉니다(`js/quiz.js` 의 `revealed`).
문제가 뜬 때가 아니라 답을 본 때라 스쳐 지나간 문제는 세지 않고, 난도를 고르자마자
되돌아 나오면 한 번도 세지 않습니다. 날짜별·달별로 쌓아(`mode:d:` · `mode:m:`)
**오늘·누적** 두 줄로 냅니다 — 누적은 달치를 모두 더한 값입니다. 난도를 고르는 화면의
각 칸 오른쪽에 적히고, 문제를 푸는 화면 맨 위의 난도 칸은 그 칸을 그대로 복제한 것이라
같은 숫자가 같은 자리에 올라옵니다. 난도를 고르면 그 칸이 제자리에서 맨 위로 미끄러져
올라가고 문제 칸이 그 아래로 떠오르며 나타납니다. 맨 위의 칸을 눌러 돌아가면 거꾸로 제자리로
내려가고 나머지 칸이 서서히 나타납니다(`moveCard` — 움직임을 줄여 달라고 한 기기에서는 옮기지
않습니다).

```
🍭 쉬움    이미지 보고 이름 선택지 3개 중 고르기    오늘 도전 3
                                                 누적 도전 2,779
```

그 숫자는 `js/stats.js` 가 이미 받아 온 응답을 `ping:stats` 이벤트로 넘겨받아 씁니다 —
요청을 두 번 보내지 않으려는 것입니다. 받는 쪽은 `addEventListener` 가 아니라
**`onStats(fn)`** 를 부릅니다. 신호가 듣는 쪽이 붙기 전에 지나갈 수 있기 때문입니다 —
`js/stats.js` 가 먼저 내려와 요청을 보내고 `js/quiz.js` · `js/page.js` 는 그 뒤에
내려오는데, 그 사이에 응답이 오면 아직 아무도 듣고 있지 않습니다. `onStats` 는 마지막
값을 들고 있다가 늦게 온 쪽에 그 자리에서 한 번 건넵니다. 새로고침하면 늘 보이던 것이
그래서입니다 — 캐시에서 곧바로 실행되어 응답보다 먼저 자리를 잡습니다.

### 배포

```bash
cd worker
npx wrangler login      # 브라우저가 열리며 Cloudflare 로그인 (한 번만)
npx wrangler deploy
```

배포하면 나온 주소를 `js/stats.js` 맨 위 `STATS_API` 에 넣습니다. 지금은 이렇게 켜져 있습니다.

```js
const STATS_API = "https://teenieping-counter.elsewon.workers.dev";
```

**`STATS_API` 가 비어 있으면** 아무 요청도 보내지 않고 통계 줄도 나타나지 않습니다.
통계를 잠시 끄고 싶으면 이 값을 비우면 됩니다.

`ALLOW_ORIGIN` 이 `https://elsewon.github.io` 라서 **배포된 사이트에서만 숫자가 올라갑니다.**
`file://` 로 열거나 로컬 서버로 볼 때는 Worker 가 403 으로 막고, 통계 줄은 조용히 숨겨집니다.

### 읽기는 엣지에 캐시한다

**증상**: 통계·인기 차트가 이따금 몇 초씩 늦게 떴습니다. 재 보니 요청 셋 중 하나꼴로
1초를 넘고 최대 6~10초였습니다.

**원인**: `wrangler tail` 로 보면 **Durable Object 안에서 하는 일은 늘 0~1ms** 인데
바깥 Worker 가 CPU 를 0ms 쓰면서 몇 초를 기다립니다. 계산도 데이터 양도 아니고
**DO 에 닿는 것 자체**가 느립니다. 이 사이트는 방문이 하루 십수 번뿐이라 DO 가 거의
늘 잠들어 있고, 깨우는 값을 그때 온 방문자가 그대로 뭅니다.

```
/nope  (DO 안 거침)   0.14~0.18s   흔들림 없음
/stats (DO 거침)      0.18s ~ 9.9s
```

**고침**: 읽기 응답(`/stats` `/rank` `/series` `/refs`)을 엣지에 두고, 만료돼도
**일단 그것을 내준 뒤 뒤에서 새로 받아 채워 넣습니다**(stale-while-revalidate).

```
max-age               60초    이 안이면 그대로 (HIT)
stale-while-revalidate 하루    묵어도 즉시 내주고 뒤에서 갱신 (STALE)
```

짧은 캐시만으로는 소용이 없습니다 — 방문 사이가 평균 한 시간이 넘어 다음 사람이 올 때는
이미 만료입니다. **묵은 것이라도 즉시 내주어야** 아무도 DO 를 깨우느라 기다리지 않습니다.

세는 일(`POST /hit`)은 캐시하지 않습니다. 그래서 **세션 첫 페이지는 늘 최신**을 봅니다
(그 응답을 그대로 씁니다). 뒤처지는 것은 "그 사이 남이 올린 숫자" 뿐입니다.

응답의 `x-cache` 헤더로 `HIT` · `STALE` · `MISS` 를 밖에서 볼 수 있습니다 — 느린 응답이
정말 캐시를 못 맞힌 것인지 확인하려면 알아볼 길이 있어야 합니다.

**통계 페이지(`stats.html`)만 캐시를 건너뜁니다** — 읽기 주소에 `fresh=1` 을 붙입니다.
숫자를 확인하러 들어가는 곳인데 묵은 값을 주면 **새로고침을 두 번 누르게 됩니다**
(첫 번째는 옛 값, 그 사이 뒤에서 갱신되어 두 번째에 새 값). 꼬리말 숫자와 인기 차트는
그대로 캐시를 씁니다.

> `fresh=1` 로 받아 온 것도 캐시에 넣습니다 — 그 덕에 다음 방문자는 빨라집니다.
> 캐시 열쇠에서는 `fresh` 를 뺍니다. 그러지 않으면 `fresh=1` 요청이 딴 칸에 쌓여
> 보통 요청과 서로 남의 것을 못 봅니다.

| | 중앙값 | 90% | 최대 | 1초 초과 |
|---|---|---|---|---|
| 전 | 0.22s | 3.74s | 6.43s | 14/40 (35%) |
| 후 | 0.18s | 0.19s | 0.20s | **0/40** |

**클라이언트에는 5초 시간 제한**을 두었습니다(`js/util.js` 의 `timeoutSignal`).
그전에는 제한이 없어 느릴 때 "불러오는 중…" 인 채로 매달렸습니다. 통계는 부가 기능이라
못 받아도 사이트는 그대로 동작합니다.

### 알아 둘 점

- **공유** 는 세지 않습니다. 브라우저 자체 공유나 주소창 복사는 사이트의 js 를 거치지 않아
  **셀 수 있는 공유가 실제 공유의 일부뿐**이었습니다 (위 [공유를 아예 빼기까지](#공유를-아예-빼기까지)).
  공유 버튼과 `?s=1` 표식은 그대로라 방문 경로에는 계속 잡힙니다.
- **하루 경계** 는 한국 시각 기준입니다 (Worker 는 UTC 로 도므로 `worker/counter.js` 에서 +9 시간).
- 광고 차단기가 요청을 막으면 실제보다 적게 집계됩니다. 정확한 수치가 아니라 대략의 흐름으로 보세요.
- `/hit` 은 `ALLOW_ORIGIN` 에 적힌 출처에서 온 POST 만 받습니다 (`worker/wrangler.toml`).
  배포 주소가 바뀌면 이 값도 함께 고치세요.
